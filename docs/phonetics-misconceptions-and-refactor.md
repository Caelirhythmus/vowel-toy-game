# 《元音演变推理小游戏》语音学事实误区研究与重构思路

> 研究对象：`index.html` / `script.js` / `style.css`（CVCV 伪词 + 开口度判定的二元推理游戏）
> 文档用途：列出该项目可能向学习者传递的语音学事实误解，并给出重构路线。

---

## 0. 项目的“事实模型”速览

游戏把以下命题当作“规则”写进了代码和说明页：

1. 元音集合：`i, e, ɛ, æ, a`，并按“开口度”排成一条线：`i(0) < e(1) < ɛ(2) < æ(3) < a(4)`。
2. 词形：CVCV，辅音 `b, p, m, d, t, n, h, g, k`，两词对应位置辅音相同。
3. **演变判定**：A→B 可能 ⇔ 每个元音位置都满足 `opening(A) ≥ opening(B)`。
   - 即：**只允许“开口度大 → 开口度小”（高化），不允许低化**；相等也算“能变”。
4. 辅助设定：限时作答、答错扣 1 秒。

下面逐条对照真实语音学事实。

---

## 1. 语音学事实误区研究

### 1.1 单维化：把“开口度”当成元音音质的唯一维度

**语音学事实**：元音音质至少由**舌位高低（height）**和**舌位前后（backness）**两个维度决定，再加上圆唇（rounding）、长短、松紧（ATR）、鼻化、卷舌等特征。IPA 元音图是一个二维梯形，不是一条线（[Oxford Phonetics: Cardinal Vowels](https://www.phon.ox.ac.uk/jcoleman/CardinalVowels.htm)；[Essential of Linguistics §2.7 Classifying Vowels](https://open.maricopa.edu/essentialsoflinguistics/chapter/2-8-vowels/)；中文介绍可参考[知乎《语音学笔记 | Vowel》](https://zhuanlan.zhihu.com/p/145158448)）。

**问题**：`i, e, ɛ, æ, a` 恰好是同一列（前、不圆唇）元音，所以“开口度”排序在该子集内部成立；但游戏把它偷换成了“元音演变的唯一判据”。一旦引入 `u`（高、后、圆唇），它的开口度与 `i` 相同——按游戏规则 `i→u` 应判“能变”，可它实际是**前后/圆唇**变化，与开口度无关。

**可能的误解**：学习者会以为“元音 = 一条线上的开合度”，不知道元音空间是二维的，也不知道 [æ] 与 [a]、[i] 与 [u] 的差异根本不在开口度上。

**术语补充**：中文语音学教材里“开口度”通常与“舌位高低”互换使用（高/半高/半低/低），但它与下颚实际开合度只是相关而不等同；游戏把这一近似术语直接当成了可公理化的离散标量，没有说明这只是近似。

---

### 1.2 方向性绝对化：只允许高化，不允许低化

**设定出处**：汉语历史音韵学里“**元音高化**”确实是被反复讨论的重要倾向——王力《汉语史稿》《汉语语音史》有系统论述，现代方言研究也确认“元音高化和高元音的高顶出位是元音变化的重要方式”（[万方：金雪婷论文摘要](https://s.wanfangdata.com.cn/paper?q=%E4%BD%9C%E8%80%85%3A%22%E9%87%91%E9%9B%AA%E5%A9%B7%22)）。游戏规则大概率是对这一倾向的转写。

**但它是统计倾向，不是定律。** 低化、央化、前化、复元音化在跨语言中同样常见：

- **低化**：日耳曼语的 a-mutation 让短 `u` 在含非高元音（通常 `a`）的下一个音节前低化为 `o`（[Wikipedia: Germanic languages](https://en.wikipedia.org/wiki/Germanic_language_group#3)）；英语 FOOT–STRUT 裂变也是 `ʊ→ʌ` 的低化。
- **央化/弱化**：非重读元音弱化为 `ə` 是所有重音语言的家常便饭（[Wikipedia: Vowel reduction](https://en.wikipedia.org/wiki/Centralized_vowel#1)）。
- **条件性高化/前化**：i-umlaut 让后元音在词尾 `i/j` 前高化并前化（`u→y, o→ø, a→e`）（[Wikipedia: I-umlaut](https://en.m.wikipedia.org/wiki/I-umlaut#1)）——方向虽然“高化”，但触发条件是**别的音节的元音**，游戏模型完全无法表达。
- **复元音化 + 低化**：英语元音大推移（GVS）中 `iː→aɪ` 是复元音化且整体走向低化，与同一条链上的 `eː→iː` 高化并存；GVS 究竟该分析为推链还是拉链、先高化还是先低化，学界至今有争议（[Lutz, The First Push: A Prelude to the Great Vowel Shift](https://www.semanticscholar.org/paper/The-First-Push%3A-A-Prelude-to-the-Great-Vowel-Shift-Lutz/628be9fd87d803f58e0de9353bb6950717373a90)；[KCI 相关研究](https://kci.go.kr/kciportal/landing/article.kci?arti_id=ART001696706)）。

**可能的误解**：把“只升不降”当成音变公理。按此规则，`u→o`、`i→e`、`a→ə` 等大量真实演变会被学生判为“不可能”。

---

### 1.3 “演变”的时间方向被架空

**语音学事实**：历史音变的方向靠**比较法、文献证据、内部重建**推断，不是由开口度大小推出的。`a` 未必古于 `e`——原始印欧语 `*u` 在日耳曼语里低化为 `*o`（a-mutation），方向与游戏规则正好相反。

**问题**：游戏里 `A → B` 的箭头没有任何时间层次说明——是历时音变（A 更古）？还是共时交替（如英语 sing/sang/sung）？还是任意造词之间的“变形”？三者是不同性质的现象。

**可能的误解**：学习者会以为“开口度大的词就是古词”、“开口度决定历史方向”。

---

### 1.4 词汇层 vs 音系层：规则音变的系统性被抹除

**语音学事实**：新语法学派以来的标准观点是，**规则音变（regular sound change）作用于音系系统**：在相同语音环境中，整类音、整类词一起变；词只是例子，不是变化单位。游戏每次随机生成一对伪词、单独判定这一对，暗示“词与词之间的变化是任意、逐个决定的”。

**可能的误解**：学不到“规律性”这一历史语言学最重要的方法论支柱，以为音变是孤立词对之间的随机事件。

---

### 1.5 环境制约被抹除：强制“辅音相同”

**语音学事实**：大量元音演变**正是由相邻辅音触发的**——umlaut（`i/j` 触发前化高化）、鼻化（鼻音前）、r 化、w 后圆唇化、腭化环境高化等；同时辅音自身也会演变（腭化、弱化、清化）。

**问题**：游戏强制两词辅音相同，等于宣告“元音演变与辅音环境无关、辅音永不变”。这恰好排除了语音学上最典型的条件音变（i-umlaut 的触发音就在下一个音节里）。

**可能的误解**：辅音只是背景板；音变是“无条件”的。

---

### 1.6 无重音、无音节位置

**语音学事实**：重读/非重读元音的演变路径截然不同——弱化、脱落几乎只发生在非重读位置；开/闭音节、词首/词尾位置也影响演变。CVCV 中两个 V 被平等对待，没有任何重音信息。

**可能的误解**：同一词里所有元音“要么都变要么都不变”（游戏按位置分别判定，比“整词同变”稍好，但仍没有重音这一最重要的分化条件）。

---

### 1.7 记音符号与音标意识缺失

**问题**：`i, e, ɛ, æ, a` 是 **IPA 音标**，不是字母表；页面却把它们当普通单词字符展示，没有任何“这是音标”的说明。`[a]` 是前不圆唇开元音，而英语 father 多为 `[ɑː]`、普通话“啊”常为 `[ä]/[ɑ]`——游戏的 “a” 没有指代任何语言。此外 `ɛ`/`æ` 在部分系统字体下会渲染成方框。

**可能的误解**：把音标当正字法；把 `[a]` 当成“万能的 a”。

---

### 1.8 “能/不能”二元判定：把统计倾向包装成逻辑律

**语音学事实**：音变“可能性”本质上是**类型学概率问题**——哪种演变类型跨语言更常见、在该语言该环境中是否真的发生。“高化倾向”是归纳出来的统计倾向，不是由开口度推出的演绎必然。

**可能的误解**：认识论倒置——学生把倾向当成自然定律去“推理”，而不是去了解“哪些演变类型常见、由什么条件触发”。

---

### 1.9 附带：游戏自身逻辑瑕疵（非语音学，但损害教学可信度）

| 问题 | 说明 |
|---|---|
| A == B 判“能变” | 两词完全相同（“什么都没变”）也被算作“Can Change”，概念上说不通 |
| 双重扣时 | 答错时 `timeLeft--` 与 `setInterval` 每秒递减可能同秒双扣 |
| 答案分布偏斜 | 随机生成下 P(能变) = 0.6 × 0.6 ≈ 0.36，约 2/3 的题答案是 “No” |
| 反馈无解释 | 只报对/错，从不说明“为什么这类演变典型/不典型” |
| 标题误导 | “Vowel Change Inference”按开口度推断一切元音演变（见 1.1、1.2） |

---

## 2. 一句话结论

> 该项目把历史音韵学中“**元音高化倾向**”这一统计性倾向，压缩成一维“开口度”标量上的**绝对方向律**，同时抹掉了二维元音空间、环境制约、重音和规则音变的系统性。
> 作为“高化倾向”专项训练器勉强可用；作为“元音演变”通识教学，会传递多处事实误解。

## 3. 重构思路

### 3.1 第一步：重新定位（最重要）

二选一，并同步改名：

- **方案 A（保守）**：保留“高化判断题”玩法，正名为《元音高化倾向推理小游戏》。页内加“模型说明 / 免责”面板：只模拟“高化”这一种演变倾向；明确写明“低化（如 u→o、i→e）、央化（非重读→ə）、复元音化在真实语言中同样常见”。
- **方案 B（推荐）**：升级为《元音演变类型学习游戏》，内容单元从“一条开口度规则”改为“演变类型 × 环境制约”。

### 3.2 内容层重构（数据驱动）

1. **元音建模为特征向量**，而不是离散标量：
   ```js
   { symbol: 'i', height: 4, backness: 'front', rounded: false, length: 'short' }
   ```
   并用 IPA 元音图（二维梯形）渲染位置，可展示圆唇配对（i/y、u/o）与长短对立。

2. **演变规则表（声明式）**，覆盖常见类型并附真实语料：
   ```js
   rules = [
     { type: '高化',   trigger: null,         example: 'GVS: eː→iː' },
     { type: '低化',   trigger: '后接 a 音节', example: '日耳曼 a-mutation: u→o' },
     { type: '前化',   trigger: '后接 i/j',    example: 'i-umlaut: u→y, a→e' },
     { type: '央化弱化', trigger: '非重读',     example: 'ə' },
     { type: '复元音化', trigger: null,        example: 'GVS: iː→aɪ' },
     ...
   ]
   ```

3. **判定语义升级**：从“能/不能”改为“**典型 / 偶见 / 罕见**”（三档），或按跨语言频率给分；若必须保留方向性判定，也至少标注“仅统计倾向，非定律”。

4. **加入环境字段**：重音（ˈ）、邻接辅音、开/闭音节。CVCV 可换成带环境的拟真词形，例如 `CəCV`（轻读音节）对比 `CˈVCV`（重读音节）。

5. **系统级玩法（直接训练“规律性”）**：给一个小型音系和一条演变规则（如“重读音节中的 a → e”），让玩家预测**整张词表**的变化，或从词表中找出不符合规则的例外词——这才是历史音变推理的正确姿势（规则音变作用于系统，不是词对词）。

### 3.3 代码架构重构

- **三层拆分**：
  - `core/`（纯函数、可单测）：元音/词形数据、演变判定、题目生成器（保证 yes/no 配平、排除 A==B、难度参数化）；
  - `state/`：有限状态机 `idle → running → answering → gameover`，消灭 reset/start 里重复手写的十几行状态代码；
  - `ui/`：单一 `render(state)` + 事件委托，DOM 操作集中。
- **修 bug**：计时改用时间戳差值（`Date.now()`），避免 setInterval 漂移与双重扣时；A==B 直接排除或判“未变”；题目生成按目标答案比例配平。
- **工程约束**：保持纯静态、零构建（GitHub Pages 直接传仓库），ES Modules 即可，不必引入框架；`deploy.yml` 无需改动。
- **可访问性与国际化**：`aria-live` 反馈区、键盘操作、弹窗焦点陷阱、`prefers-reduced-motion`；页面已半中半英，可顺手做完整中英双语。

### 3.4 游戏机制重构

- **难度分级**：单元音位 vs 双元音位；纯高化 vs 混合演变类型；无环境 vs 带环境。
- **反馈即教学**：每次作答后展示演变类型名称 + 真实语言例子（如“u→o：日耳曼 a-mutation；i→e：低化，真实存在，但非本关练习方向”）。
- **结算报告**：错题回顾 + 常见混淆点提示。
